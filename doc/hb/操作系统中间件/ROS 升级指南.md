# ROS1 与 ROS2 关键差异

## 一、整体定位差异

* **ROS1**：学术友好、上手快，偏原型与单机系统
* **ROS2**：工业导向、分布式与实时系统设计，面向量产与长期维护

---

## 二、核心架构对比

| 维度     | ROS1                 | ROS2                |
| ------ | -------------------- | ------------------- |
| 中心节点   | 依赖 `roscore`（Master） | 无 Master，完全去中心化     |
| 通信中间件  | TCPROS / UDPROS      | DDS（可选多种实现）         |
| 发现机制   | 集中注册                 | 自动发现（DDS Discovery） |
| 节点崩溃影响 | Master 影响全局          | 单点故障不影响整体           |

➡️ **ROS2 天然支持多机、多进程、跨网络部署**

---

## 三、通信模型与性能

### Topic / Service / Action

| 项目      | ROS1       | ROS2                     |
| ------- | ---------- | ------------------------ |
| Topic   | 无 QoS      | 有 QoS（可靠性、历史深度等）         |
| Service | 同步阻塞       | 基于 DDS，请求-响应更规范          |
| Action  | ros_action | 原生支持（更稳定）                |
| 大数据传输   | 易阻塞        | DDS 零拷贝 / Loaned Message |

### QoS（ROS2 核心优势）

* Reliable / Best Effort
* History（Keep Last / Keep All）
* Durability（Transient Local）

➡️ **传感器、控制、日志可采用不同 QoS 策略**

---

## 四、实时性与嵌入式支持

| 项目       | ROS1    | ROS2                    |
| -------- | ------- | ----------------------- |
| 实时系统     | 几乎不支持   | 支持 RT Linux / QNX       |
| Executor | 单线程回调为主 | Multi-threaded Executor |
| 内存控制     | 动态分配多   | 可避免运行期分配                |
| 嵌入式      | 非常有限    | 支持 micro-ROS            |

➡️ **ROS2 可用于控制闭环与硬实时边缘节点**

---

## 五、工程化与部署

| 维度     | ROS1     | ROS2                   |
| ------ | -------- | ---------------------- |
| 生命周期管理 | 无        | Node Lifecycle（可控状态机）  |
| 安全     | 几乎没有     | DDS-Security（加密 / 认证）  |
| 跨平台    | Linux 为主 | Linux / Windows / RTOS |
| 长期维护   | 已停止新特性   | 官方主线                   |

---

## 六、生态与成熟度（现实情况）

* ROS1

    * 教程、示例多
    * 老项目多，稳定
    * 新功能基本冻结

* ROS2

    * 导航（Nav2）、SLAM、控制栈已成熟
    * 工业公司主流选择
    * API 偏工程化，学习成本更高

---

## 七、迁移成本评估（重点）

### 迁移难点

* 通信 API 不兼容（`ros::NodeHandle` → `rclcpp::Node`）
* 参数系统完全重写
* Launch 文件从 XML → Python
* 自定义消息需重新编译
* 部分 ROS1 包无 ROS2 版本

### 可行迁移策略（推荐）

1. **新模块直接使用 ROS2**
2. 通过 `ros1_bridge` 过渡
3. 保留算法逻辑，重写通信层
4. 先迁移：

    * 底盘控制
    * 传感器驱动
    * 导航 / 调度系统

---

## 八、是否值得切换（结论型建议）

**强烈建议切换 ROS2 的场景：**

* 多机 / 多机器人
* 工业级 AGV / AMR
* 需要长期维护与量产
* 对实时性、稳定性有要求

**可暂缓切换的场景：**

* 教学 / Demo
* 单机、低复杂度系统
* 维护成本远高于收益

---




以下为**ROS1 → ROS2 迁移清单**，按“可执行、可落地”的工程视角整理，适合直接作为迁移对照表或评审清单使用。

# ROS1 → ROS2 迁移清单

## 一、整体迁移策略确认（先做这一步）

* ☐ 是否采用 **渐进式迁移**（推荐）
* ☐ 是否启用 `ros1_bridge` 作为过渡
* ☐ 新功能是否 **只在 ROS2 开发**
* ☐ 目标 ROS2 发行版（Foxy / Humble / Iron / Jazzy）

---

## 二、代码与 API 层面

### 1️⃣ 节点与基础 API

| ROS1              | ROS2                     | 迁移状态 |
| ----------------- | ------------------------ | ---- |
| `ros::init`       | `rclcpp::init`           | ☐    |
| `ros::NodeHandle` | `rclcpp::Node`           | ☐    |
| `ros::spin()`     | Executor（Single / Multi） | ☐    |
| `ros::Rate`       | `rclcpp::Rate`           | ☐    |
| 回调队列              | Callback Group           | ☐    |

---

### 2️⃣ Topic 通信

* ☐ `advertise()` → `create_publisher()`
* ☐ `subscribe()` → `create_subscription()`
* ☐ 明确 QoS 策略（Sensor / Control / Log）
* ☐ 大数据 Topic 是否启用 Loaned Message
* ☐ Topic 名称是否涉及 namespace 重构

---

### 3️⃣ Service / Action

* ☐ Service API 重写（同步模型变化）
* ☐ Action 改用 ROS2 原生 Action
* ☐ 客户端超时与异常处理补齐
* ☐ 原有 blocking 调用是否影响 Executor

---

### 4️⃣ 参数系统（**高风险项**）

* ☐ 参数需显式声明（`declare_parameter`）
* ☐ 动态参数回调重写
* ☐ 参数文件格式调整（YAML）
* ☐ 参数命名空间重新梳理
* ☐ 启动期参数与运行期参数区分

---

## 三、构建与包管理

### 5️⃣ 构建系统

| 项目   | ROS1           | ROS2                       |
| ---- | -------------- | -------------------------- |
| 构建工具 | catkin         | ament_cmake / ament_python |
| 编译依赖 | package.xml v2 | package.xml v3             |
| 导出接口 | catkin_package | ament_export               |

* ☐ `CMakeLists.txt` 重写
* ☐ `package.xml` 升级
* ☐ 依赖库是否有 ROS2 版本

---

### 6️⃣ 自定义消息

* ☐ `.msg / .srv / .action` 重新编译
* ☐ 消息包独立化
* ☐ 接口稳定性评审
* ☐ ros1_bridge 是否需要映射

---

## 四、Launch 与运行管理

### 7️⃣ Launch 文件（变化最大）

* ☐ XML → Python Launch
* ☐ 参数加载方式变更
* ☐ 条件启动 / 组合节点重构
* ☐ 多进程 vs Component 架构确认

---

### 8️⃣ 节点生命周期（ROS2 独有）

* ☐ 是否启用 Lifecycle Node
* ☐ 状态迁移是否纳入调度逻辑
* ☐ Nav2 / 控制节点生命周期对齐

---

## 五、系统级能力

### 9️⃣ 实时性与性能

* ☐ Executor 模型选择
* ☐ 回调是否隔离（Callback Group）
* ☐ 内存分配是否可控
* ☐ 控制链路是否满足实时要求

---

### 🔟 多机与网络

* ☐ DDS 实现选择（FastDDS / CycloneDDS）
* ☐ Discovery 网络策略
* ☐ QoS 与网络抖动匹配
* ☐ 跨子网 / NAT 场景验证

---

### 1️⃣1️⃣ 安全机制（可选）

* ☐ 是否启用 DDS-Security
* ☐ 证书管理流程
* ☐ 加密对性能影响评估

---

## 六、工具链与运维

### 1️⃣2️⃣ 调试与日志

* ☐ `rosbag` → `rosbag2`
* ☐ QoS 兼容性导致的 bag 回放问题
* ☐ `rqt` 插件替换情况
* ☐ 日志等级与输出方式确认

---

### 1️⃣3️⃣ CI / 部署

* ☐ Docker 镜像更新
* ☐ 多架构交叉编译（ARM / x86）
* ☐ 系统启动脚本调整
* ☐ OTA / 升级策略适配

---

## 七、第三方依赖评估

* ☐ 底盘 / 雷达 / 相机驱动 ROS2 支持情况
* ☐ SLAM（Cartographer / SLAM Toolbox）
* ☐ 导航（move_base → Nav2）
* ☐ 控制（ros_control → ros2_control）

---




# 清洁机器人 ROS2 传感器驱动迁移指南

> **ROS2 迁移的最大不确定性，不在算法，不在框架，而在传感器驱动是否“被时代抛弃”。**

对清洁机器人而言：

* 算法可控
* 架构可改
* **驱动不可控**

因此，第三方评估应**前置为“供应链审计”，而不是迁移 checklist 的一个子项**。

---

## 二、室内清洁机器人典型传感器分层

### 感知层（强依赖厂商）

| 类别      | 特点          | 风险等级   |
| ------- | ----------- | ------ |
| 2D 激光雷达 | 私有协议、SDK 封闭 | ⚠️⚠️⚠️ |
| IMU     | 协议较稳定       | ⚠️     |
| 编码器     | 自研或底盘相关     | ⚠️     |
| 碰撞 / 悬崖 | MCU 直连      | ⚠️     |

➡️ **真正的高风险只有一个：2D 激光雷达**

---

## 三、2D 激光雷达

### 1️⃣ 现实情况

* 清洁机器人使用：

    * 串口 / USB
    * 私有二进制协议
    * ROS1 驱动“勉强能跑”
* ROS2 驱动：

    * 要么没有
    * 要么多年未维护
    * 要么官方只给 SDK，不给 ROS2 封装

---

### 2️⃣ 迁移风险分类

| 风险类型    | 表现              |
| ------- | --------------- |
| 驱动缺失    | 无 ROS2 版本       |
| API 锁死  | SDK 仅支持 ROS1    |
| 维护中断    | 最后提交 3～5 年前     |
| QoS 不兼容 | DDS 丢包或发现失败     |
| 性能退化    | ROS2 CPU 占用明显上升 |

---

### 3️⃣ 工程化应对策略

#### ✅ 策略一：驱动下沉（推荐）

```
雷达驱动 = 独立进程 / 独立库
        ↓
标准化数据结构（LaserScan-like）
        ↓
ROS1 / ROS2 双封装
```

* 雷达协议解析 **脱离 ROS**
* ROS 仅作为通信层
* 后续切换中间件成本极低

---

#### ✅ 策略二：ROS1 驱动 + ros1_bridge（过渡）

* 快速上线
* 适合试点或验证阶段
* **不适合量产长期方案**

---

## 四、IMU

### 现实情况

* 协议公开（串口 / SPI / I2C）
* ROS2 驱动普遍可用
* 但 **时间戳与同步问题常被忽略**

### 迁移关注点

* ☐ 硬件时间戳 vs 软件时间戳
* ☐ DDS QoS 是否影响高频 IMU
* ☐ 是否需要 `SensorDataQoS`

---

## 五、编码器（轮式里程计）

### 两种常见模式

#### 模式 A：ROS 层直接读编码器（不推荐）

* 强依赖驱动
* 实时性差
* ROS2 中问题更明显

#### 模式 B：MCU 汇总 → 上位机（推荐）（目前是这种）

* 编码器 → MCU
* MCU → 串口 / CAN
* ROS2 只消费里程计结果

---

## 六、碰撞 / 悬崖传感器

* 数字量 / 模拟量
* 通常由 MCU 统一采集
* ROS 只收结果

迁移关注点：

* Topic QoS（Best Effort 即可）
* 消息节流，避免 Executor 被打爆
