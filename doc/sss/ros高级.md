# 一、ROS 架构 & 通信（必考）

## **1️⃣ ROS1 的整体架构是怎样的？为什么需要 roscore？**

### 追问：

* roscore 挂了会发生什么？
* Master 负责转发数据吗？
* ROS2 为什么去掉 Master？
* ROS1 和 ROS2 在“发现机制”上的本质差异？

ROS1 依赖 roscore（Master）做节点注册和发现，Master 不转发消息，挂掉影响新节点连接；ROS2 用 DDS 去中心化发现，提高可靠性，节点间自动发现，解决了 ROS1 中心化单点故障问题。

# 二、Node / 生命周期（中高级分水岭）

## **3️⃣ ROS Node 的生命周期是怎样的？**

ROS Node 是计算单元，其生命周期从启动到退出包括 初始化、注册、运行、关闭。
生命周期主要包括：
创建节点：分配资源、初始化通信接口
注册到 Master（ROS1）/发现到 DDS（ROS2）
初始化发布者/订阅者、服务、参数等
运行：节点进入循环，处理回调函数
关闭：清理资源，注销节点，结束通信

### 追问：

* ROS1 和 ROS2 生命周期有什么不同？
* ROS2 Lifecycle Node 解决了什么问题？
* 一个节点从启动到退出，经历了哪些状态？
* 节点异常退出，系统如何感知？
* launch / launch_ros 在生命周期中起什么作用？

ROS Node 生命周期包括创建、注册、初始化、运行和关闭；ROS2 增加 Lifecycle 管理可控状态机，确保节点按阶段安全启动和退出，launch 文件用于批量管理节点和生命周期操作。

## **4️⃣ 一个 ROS 节点频繁“卡死”，你如何排查？**

### 追问：

* 回调阻塞会带来什么后果？
* 单线程 vs 多线程 spinner 区别？
* callback queue 是什么？
* ros::spin() 和 ros::spinOnce() 区别？
* ROS2 executor 是怎么调度回调的？

观察节点状态：使用 rosnode info <node> 查看订阅、发布、服务是否正常
检查回调函数：回调是否存在耗时操作或死循环，是否阻塞 spinner
分析 spinner 配置：单线程 spinner 是否阻塞整个节点，多线程 spinner 是否合理
查看 callback queue：是否消息积压导致处理延迟
工具辅助：rqt_console / rostopic echo / roslaunch --screen / gdb attach 或 perf 分析栈
合理拆分节点：耗时任务可用异步线程或 action 分离，避免阻塞主循环

节点卡死多因回调阻塞或消息积压，单线程 spinner 会阻塞队列，多线程 spinner 并发处理回调；ROS2 用 Executor 管理回调，callback queue 决定消息处理顺序，合理拆分耗时任务可避免阻塞。

# 三、话题 & 通信机制（核心）

## **5️⃣ ROS Topic 的通信过程是怎样的？**

节点注册：发布者（Publisher）和订阅者（Subscriber）启动时，向 ROS1 Master 注册 Topic 名称和通信信息
节点发现：订阅者向 Master 查询 Topic 对应的发布者信息
建立连接：订阅者获取发布者的 IP/端口，建立 TCP 或 UDP 连接（TCPROS / UDPROS）
消息传输：发布者将消息发送到订阅者，订阅者从回调队列中读取并处理
通信完成：节点退出或 Topic 注销时，连接关闭，Master 更新注册信息

### 追问：

* 发布者和订阅者如何发现彼此？
* TCPROS 和 UDPROS 区别？
* latch topic 是什么？适合什么场景？
* QoS 在 ROS2 中解决了什么？
* ROS2 的 DDS 是怎么保证可靠性的？

ROS Topic 通信：节点注册 → 发现 → 建立连接 → 消息传输 → 注销；ROS1 依赖 Master，ROS2 DDS 去中心化，TCPROS 可靠、UDPROS 高速，latch 适合一次性广播，ROS2 QoS 与 DDS 保证可靠性和顺序。

---

## **6️⃣ ROS 中消息序列化是怎么做的？**

ROS 通信消息需要在节点间传输，在内存中结构化对象 → 网络字节流
序列化（serialize）：将消息对象打包成字节流
反序列化（deserialize）：收到字节流后解析成消息对象
ROS1 使用自定义的 C++/Python 序列化机制，ROS2 基于 IDL / DDS 进行序列化
消息定义由 .msg / .srv / .action 文件生成对应语言的类型支持

### 追问：

* msg / srv / action 的区别？
* 消息变更后如何兼容？
* 为什么 ROS 不直接用 protobuf？
* 零拷贝通信是如何实现的？
* ROS2 intra-process 通信的原理？

ROS 消息序列化负责将对象 → 字节流传输，msg/srv/action 分别对应异步、同步和带反馈任务；ROS 自研序列化支持零拷贝和高效回调，ROS2 intra-process 利用 shared_ptr 在同进程内直接传递消息，避免序列化开销。

# 四、坐标系 & TF（必问）

## **7️⃣ TF / TF2 是干什么的？**

TF / TF2 用于 管理和转换不同坐标系之间的关系
可以在多个传感器、机器人部件之间统一空间参考
节点通过 广播 (tf broadcaster) 发布坐标系变换，通过 订阅 (tf listener) 查询变换
TF2 是 ROS2 的升级版，性能更高，线程安全，支持缓存和延迟查询

### 追问：

* tf 和 tf2 的区别？
* 为什么要用时间戳？
* 如何避免 TF 树断裂？
* map → odom → base_link 的设计目的？
* TF 查询失败的常见原因？

TF / TF2 管理坐标系变换，保证机器人各部分和传感器数据空间一致，使用时间戳对齐历史数据，map → odom → base_link 分离全局一致性和局部实时性，TF2 提高性能和线程安全，避免树断裂和时间戳错误即可保证查询成功。

# 五、参数 & 配置管理（工程能力）

## **8️⃣ ROS 参数服务器是如何工作的？**

ROS 参数服务器（Parameter Server）用于 存储节点可访问的配置信息，包括整数、浮点、字符串、列表、字典等类型
节点启动时可读取参数，也可动态修改
参数存储在 Master 节点内存中，通过 XMLRPC 接口访问
节点通过 rosparam 或 API 获取、设置参数，实现全局可见

### 追问：

* 参数是存在哪的？
* 参数动态修改如何生效？
* dynamic_reconfigure 的原理？
* ROS2 参数和 ROS1 的差异？
* 为什么不建议把参数当“配置中心”？

ROS 参数服务器是全局内存键值对存储节点参数，dynamic_reconfigure 提供动态修改回调，ROS2 将参数存储节点本地并可 DDS 同步，参数不持久化不适合作为配置中心。

# 六、实时性 & 性能（高级）

## **9️⃣ ROS 系统如何保证实时性？**

ROS 本身运行在 Linux 用户态，消息传输通过 TCP/UDP 网络，不保证固定时间延迟，因此 天生不实时
保证实时性需要：
控制回调处理时间，避免阻塞
使用 多线程 executor / spinner 分流回调
在 实时操作系统（RTOS）或实时内核 Linux 上运行
在 ROS2 中配置 DDS QoS，如 deadline、latency_budget、reliability 等
核心思路：尽量减少系统阻塞和不确定延迟，使用优先级调度和内核实时特性

### 追问：

* ROS 为什么“天生不实时”？
* 哪些地方最容易引入抖动？
* executor / callback 优先级怎么控制？
* 如何与 RTOS / 实时 Linux 协作？
* DDS QoS 中哪些参数影响实时性？

ROS 天生不实时，实时性依赖回调优化、多线程 executor、DDS QoS 配置和实时操作系统协作，核心是减少阻塞和不确定延迟，分离实时与非实时路径。

# 七、系统设计 & 工程（高级）

## **🔟 设计一个“稳定运行 7×24 的 ROS 系统”，你会考虑哪些点？**

节点自恢复：使用 watchdog 或外部管理进程（如 roslaunch respawn、systemd、supervisor）自动重启异常节点
日志与监控：ROS 自带 rosbag / rosconsole 记录日志，结合 Prometheus / Grafana / ELK 做系统监控与告警
Launch 管理：使用 roslaunch / launch 将多节点系统编排，支持依赖、参数注入、节点分组
灰度升级：先部署低风险节点 / 测试节点，逐步替换核心节点，保证系统稳定
ROS1 → ROS2 迁移：需关注 topic / service / action 接口变化、TF2 替换 TF1、QoS 配置、executor 模型差异、参数系统变化

### 追问：

* 节点异常退出如何自恢复？
* 如何做日志、监控、告警？
* launch 如何管理复杂系统？
* 如何灰度升级 ROS 节点？
* ROS1 → ROS2 迁移的主要坑？

7×24 ROS 系统稳定性依赖节点自恢复、日志监控告警、launch 编排、灰度升级以及 ROS1→ROS2 的接口和 QoS 差异迁移，核心是故障隔离、快速恢复、可观测与渐进升级。

# 八、算法 / 业务结合题（加分项）

## **1️⃣1️⃣ 感知 / 控制算法如何优雅地接入 ROS？**

解耦 ROS 回调与算法模块：ROS 回调负责数据收集、消息解包和发布，算法模块独立处理逻辑
线程分离：使用消息队列、异步任务或多线程 executor，保证回调快速返回，算法独立执行
接口标准化：算法模块使用 纯函数或类接口，ROS 只做消息传入和结果输出
测试友好：算法模块不依赖 ROS，可通过单元测试验证逻辑正确性

### 追问：

* 算法线程和 ROS 回调如何解耦？
* 为什么不直接在回调里跑算法？
* ROS 和非 ROS 模块如何通信？
* 如何保证算法模块可单元测试？

感知/控制算法接入 ROS 的核心是 回调与算法解耦、线程分离、接口标准化、纯逻辑可测试，ROS 仅负责数据传输和结果发布，算法独立运行可保证高频、低延迟与单元测试友好。

## **1️⃣2️⃣ 多传感器系统（IMU + 相机 + 雷达）你如何设计 ROS 架构？**

每个传感器节点独立发布 topic，算法节点订阅并处理数据
使用 消息队列 / 缓冲区 / 时间戳对齐 保证同步
数据处理尽量在独立线程执行，ROS 回调仅入队，避免阻塞
设计统一 消息接口和帧 ID，确保 TF 树一致
对高频数据使用 压缩 / 零拷贝 / intra-process 减少 CPU 和带宽消耗

### 追问：

* 时间同步怎么做？
* 消息频率不一致怎么办？
* 数据丢失如何处理？
* bag 回放如何保证一致性？
* 如何减少带宽和 CPU 占用？

多传感器 ROS 系统核心是 节点解耦、时间同步、频率匹配、丢失处理和带宽优化，IMU/相机/雷达分别独立发布，算法节点异步处理，确保数据一致性和高性能。
