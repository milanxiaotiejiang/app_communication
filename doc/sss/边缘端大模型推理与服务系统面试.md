# 项目架构

### **30 秒精炼版｜主动介绍用**

“这是一个面向嵌入式平台的多模型大语言/视觉语言推理服务。我设计了统一推理框架，把多种 LLM 和 VLM 模型用 C++ 管理底层推理，通过
pybind11 暴露 Python 接口，同时加了 WebSocket 服务层，实现实时并发访问。视觉模型用 OpenCV
做图像预处理，实现从图像输入到文本输出的完整链路。整体目标是工程化、多模型统一管理和嵌入式可服务化。”

---

### **1 分钟标准版｜面试回答版**

“这个项目是针对嵌入式平台，比如 RK3588/ARM，做大模型推理服务的。我搭建了一个统一框架，把 Qwen-1.8B、DeepSeek-R1 Distill
Qwen-1.5B、Qwen2-VL-2B 等模型统一管理。底层用 C++ 做模型加载和推理，保证性能和可控性；上层通过 pybind11 暴露 Python
接口，方便算法验证和业务调用。

在此基础上，我加了 WebSocket 服务，把模型封装成可并发访问的推理服务，实现实时请求和流式返回。视觉模型部分集成了 OpenCV
做图像编码和预处理，实现完整的图像输入到文本输出链路。整个架构设计的重点是性能敏感逻辑放 C++，业务灵活性放
Python，同时考虑嵌入式依赖管理、可扩展性和长期维护能力。”

---

### **追问展开版｜面试官深挖版**

“项目核心挑战在于工程化和嵌入式可服务化，而不是模型本身。具体设计上：

1. **多模型统一管理**：同一套底层 C++ 框架可以加载多种 LLM/VLM，只在入口层区分模型类型，底层推理逻辑完全复用。
2. **性能与灵活性分层**：C++ 负责性能敏感部分，包括模型推理、图像预处理和消息队列处理；Python 用于业务逻辑、脚本接口和高层控制。
3. **服务化接口**：通过 WebSocket 封装模型为可并发服务，支持实时请求和流式返回，保证上层系统可直接调用。
4. **多模态支持**：视觉语言模型用 OpenCV 做图像编码和预处理，实现图像输入 → 特征编码 → 模型推理 → 文本输出的完整链路。
5. **嵌入式适配**：在 ARM 平台做依赖管理、RPATH 和运行库处理，保证直接板端可运行，长期可维护。

**技术含金量**在于把多个大模型、不同接口、多平台统一到一个长期可维护的工程体系里，解决的是真正复杂的工程问题，而不仅是调用
API。”

# API设计

### **30 秒精炼版**

“在 RK3588 平台上完成了本地 LLM 和多模态推理的封装。我把底层 SDK 封装成统一的运行时类，只暴露 init 和 infer
接口，避免业务层直接操作句柄，稳定可靠。推理结果通过回调机制返回，上层既能直接用默认输出，也能接自定义回调，用于 UI、Socket 或
ROS 节点。核心是工程化封装，保证嵌入式下稳定和可复用。”

---

### **1 分钟标准版**

“这个项目在 RK3588 平台上做本地 LLM / 多模态推理运行时封装。我把底层 SDK 的 C 接口封装成完整生命周期管理类，对外只提供
init、infer 等高层接口，业务层不直接接触底层句柄。推理结果通过回调机制返回，内部做了转发处理，上层可以直接使用默认输出，也能接入自定义回调，用于
UI、Socket 或 ROS 节点。

重点不是调用模型，而是工程化封装：生命周期管理、异常退出处理、资源释放、信号中断处理、多模态数据组织和推理参数可配置化。这样保证了嵌入式环境下的稳定性、可复用性和可扩展性。”

---

### **追问展开版**

“核心挑战在于在 RK3588 嵌入式平台上把 LLM 推理能力稳定地封装成可复用运行时，而不是简单调用 SDK。设计上：

1. **生命周期管理**：模型加载、推理、释放全流程管理，避免内存泄露或句柄泄露。
2. **流式回调**：推理结果通过回调返回，内部支持转发，上层可直接拿默认输出，也能接自定义回调，便于 UI、Socket 或 ROS 集成。
3. **多模态支持**：统一处理文本和图像输入，实现图文推理链路。
4. **嵌入式优化**：处理信号中断、异常退出和性能参数调优，确保 RK3588 上长期稳定运行。

# websocket服务

### **30 秒精炼版**

“在嵌入式平台上，将大模型推理封装为 WebSocket 在线服务。WebSocket 与 LLM
层完全解耦，推理请求进入队列由独立线程处理，保证流式输出同时不阻塞网络。核心是把模型当作受控资源调度，而不是简单包一层接口。”

---

### **1 分钟标准版**

“项目在嵌入式平台上搭建了轻量级 WebSocket 在线推理系统。WebSocket 层和 LLM 推理层完全解耦，通过函数注入通信，任何一层都可独立替换。

收到请求后，WebSocket 不直接触发推理，而是进入内部队列，由独立线程顺序处理，避免并发调用导致底层引擎不稳定。流式结果通过
WebSocket 实时推送，支持多客户端接入。

核心价值在于把 LLM 当作可控系统资源进行调度，而非简单暴露接口。”

---

### **追问展开版**

“这个设计的关键点在于：

1. **解耦**：WebSocket 层和推理层完全独立，函数注入实现灵活扩展。
2. **异步队列调度**：请求进入内部队列，由独立线程顺序处理，保证底层 C++ 推理引擎不会被并发调用破坏稳定性。
3. **流式输出**：WebSocket 支持实时推送生成结果，比 HTTP 更适合连续输出和减少连接开销。
4. **多客户端支持**：设计了集中调度层，统一管理模型调用和上下文生命周期，保证嵌入式环境下的稳定性和可复用性。

真实技术含金量在于 **嵌入式场景下的安全、高效、可复用推理服务架构，而不仅仅是简单的网络封装**。”

# 客户端

### **30 秒精炼版**

“这是一个基于异步消息总线的多模态语音交互系统，实现 ASR → LLM → 动作执行闭环。各模块完全解耦，通过事件驱动和职责链组织逻辑，支持
LLM 流式输出和网络自动重连，适合长期运行的机器人或语音系统。”

---

### **1 分钟标准版**

“项目构建了一个异步消息总线驱动的语音交互系统，核心是将 ASR、LLM、动作执行模块完全解耦。

实时音频处理和网络通信分别由线程和 asyncio 负责，通过消息总线进行协同。LLM 的输出以流式 chunk 发布，实现边生成边处理和播报。

核心逻辑使用职责链模式，每个 Handler 专注自己的处理阶段，不依赖上下文逻辑。不同交互模式只需动态组合
Handler，就能实现多模态交互。整个系统支持自动重连和优雅退出，确保长期运行的稳定性。”

---

### **追问展开版**

“设计关键点在于：

1. **模块解耦**：消息总线让音频、LLM、动作执行、网络完全独立，任何模块异常不影响整体。
2. **异步协作**：音频采集用线程，网络与逻辑用 asyncio，各自处理最适合的任务类型。
3. **职责链模式**：Handler 只关注自己阶段，处理完成即可中断后续流程，不需要复制逻辑代码。
4. **动态组合**：通过 HandlerType 在运行时组合不同处理链，实现多模式交互。
5. **流式输出与健壮性**：支持 LLM 流式 chunk 输出和 WebSocket 自动重连，保证系统可持续运行。

真实技术含金量在于 **将多模态语音、推理与动作执行在嵌入式环境下用事件驱动架构整合成可维护、可扩展、实时运行的闭环系统**。”

# 客户端细节

### 30 秒精炼版

“这个项目实现了从语音 / 多模态输入，到 LLM 推理，再到机器人动作执行的完整闭环。核心在于消息总线解耦、LLM
输出工程化约束、动作系统插件化，以及阻塞逻辑和异步事件的正确隔离，让机器人行为可控而非被模型牵着走。”

---

### 1 分钟标准版

“系统通过消息总线连接 ASR、LLM、动作执行、音频和 ROS 模块，各模块零耦合。LLM
输出被看作不可靠组件，先转成标准化中间语义，再交给动作系统执行。动作系统采用插件化 `handle_xxx`
自动注册，新增动作无需修改解析或调度逻辑。视觉追踪和机械臂控制等阻塞逻辑通过线程池隔离，主事件循环保持异步稳定。整体设计保证多模态、流式输入下，机器人动作可控、系统长期稳定运行。”

---

### 追问展开版

“几个关键设计点：

1. **LLM 输出工程化**：流式非结构化输出先经 `LLMStreamHandler` 拼接，再由 `NetworkInHandler / ActionHandler` 做语义约束，如颜色
   ‘红 / red / reddish’ → `red`，位置 ‘一号 / 1 / first’ → `1`。
2. **消息总线解耦**：所有模块通过 `MessageBus + Topic` 通信，天然支持异步、并发，任意模块可替换或禁用。
3. **Handler Chain**：责任链 + 早停机制，每个 Handler 只处理自己职责，完成后可中断后续链路。
4. **插件化动作系统**：动作通过 `handle_xxx` 自动注册，LLM 只输出动作名和参数，实现技能扩展而非硬编码。
5. **阻塞逻辑隔离**：视觉闭环控制、机械臂操作放线程池，主事件循环不阻塞，保证实时性。
6. **视觉闭环**：HSV + 形态学 + 面积与偏移闭环控制，实现连续、可收敛的动作行为。

本质是 **把大模型的不确定性变成可控的工程系统**，让机器人行为可靠可预测，而不是直接执行模型输出。”

# 架构

### 30 秒精炼版

“项目架构分层极清晰：Input → Bus → Logic → Action → Device。消息总线作为核心中枢，逻辑层完全解耦，LLM
被视为不可靠组件，输出必须经过规则约束。动作系统插件化注册，阻塞逻辑通过线程池隔离，保证实时性和稳定性。整体目标是让机器人行为可控而非直接执行模型输出。”

---

### 1 分钟标准版

“系统严格分层：感知输入、消息总线、逻辑处理、动作调度到设备执行，每层独立可替换。消息总线负责模块通信，支持异步和并发，逻辑层无需感知数据来源。Handler
Chain 处理 ASR、LLM、语义解析、动作调度，每个 Handler 只负责单一职责，可动态组合。LLM
输出经过工程化约束才能驱动动作，动作系统插件化注册，阻塞控制逻辑统一放线程池，事件循环不阻塞，保证机器人长期稳定运行。”

---

### 追问展开版

“几个核心设计点：

1. **消息总线驱动**：所有模块通过 `MessageBus + Topic` 通信，天然支持异步、模块替换和模拟测试。
2. **Handler Chain**：责任链模式处理逻辑，各 Handler 单一职责，完成后可中断链路，支持多模式交互。
3. **LLM 工程化约束**：LLM 输出被当作意图生成器，真实动作必须经过标准化和规则化，避免不可控行为。
4. **插件化动作系统**：动作通过 `handle_xxx` 自动注册，新增动作无需修改调度逻辑，实现认知层与控制层隔离。
5. **阻塞逻辑隔离**：视觉闭环、机械臂控制等阻塞算法统一进入线程池，事件循环保持异步稳定，保证实时性和可靠性。

整体设计思想是 **把复杂度封装在系统内部，让机器人行为可控、可扩展、可长期稳定运行**。”
