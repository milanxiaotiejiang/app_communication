## **拷贝构造与移动构造（C++）**

---

### 一、拷贝构造（Copy Constructor）

**定义**
以同类型对象为参数，构造一个内容等价的新对象。

**典型签名**

```cpp
T(const T& other);
```

**语义特点**

* 资源“复制一份”，两个对象彼此独立
* 适用于值语义、需要保留原对象内容的场景
* 对含动态资源的类型，需进行深拷贝

**触发场景**

* 以值传参
* 返回值（未触发移动或被禁用时）
* 用已有对象初始化新对象

**代价**

* 可能涉及内存分配与数据复制，成本较高

---

### 二、移动构造（Move Constructor）

**定义**
从即将被销毁的临时对象中“接管”资源，避免复制。

**典型签名**

```cpp
T(T&& other) noexcept;
```

**语义特点**

* 资源所有权转移
* 源对象被置于“可析构但未定义内容”的安全状态
* 不进行深拷贝，效率高

**触发场景**

* 临时对象初始化
* `std::move` 显式转换为右值
* 返回值优化失败但可移动

**代价**

* 仅指针/句柄转移，通常为常数时间

---

### 三、核心对比

| 维度    | 拷贝构造       | 移动构造      |
|-------|------------|-----------|
| 参数类型  | `const T&` | `T&&`     |
| 资源处理  | 复制         | 转移        |
| 性能    | 较低         | 很高        |
| 源对象状态 | 保持不变       | 需被重置      |
| 典型用途  | 值语义        | 临时对象、容器扩容 |

---

### 四、与标准库的关系

* 容器优先使用 **移动构造**（若 `noexcept`）
* 未提供移动构造时，退化为拷贝
* 自定义类型若管理资源，应同时实现：

    * 拷贝构造
    * 拷贝赋值
    * 移动构造
    * 移动赋值
    * 析构函数
      （Rule of Five）

---

### 五、工程实践要点

* 移动构造建议标记 `noexcept`
* 移动后对象只保证可析构、可赋值
* 不要在移动构造中做深拷贝
* 资源型成员（指针、句柄）是移动优化的核心

---

一句话总结：
**拷贝构造负责“复制资源”，移动构造负责“接管资源”，前者保证语义完整，后者追求性能极致。**

## **`auto` 的底层机制（C++）**

---

### 一、本质定位

`auto` 并非运行期机制，而是**编译期类型推导语法糖**。
在语义分析阶段，由编译器依据初始化表达式，完成静态类型推断，随后完全等价地替换为确定类型。

> 编译完成后，代码中不再存在 `auto`。

---

### 二、核心推导规则（与模板一致）

`auto` 的类型推导规则，本质等价于**模板参数推导**。

#### 1️⃣ 基本形式（忽略引用与 `const`）

```cpp
auto x = expr;
```

等价于：

```cpp
template<typename T>
void f(T);
f(expr);
```

推导要点：

* 顶层 `const` 被丢弃
* 引用被剥离
* 得到“值类型”

示例：

```cpp
const int a = 10;
auto x = a;        // int
```

---

#### 2️⃣ `auto&`（保留引用）

```cpp
auto& x = expr;
```

规则：

* 必须绑定左值
* 保留引用与 `const`

```cpp
const int a = 10;
auto& x = a;       // const int&
```

---

#### 3️⃣ `auto&&`（万能引用）

```cpp
auto&& x = expr;
```

规则：

* 左值 → `T&`
* 右值 → `T&&`

```cpp
int a = 10;
auto&& x1 = a;     // int&
auto&& x2 = 10;    // int&&
```

等价于模板中的转发引用。

---

### 三、与 `decltype` 的关键差异

| 特性        | auto  | decltype |
|-----------|-------|----------|
| 是否求值      | 否     | 否        |
| 是否丢 const | 是（默认） | 否        |
| 是否保留引用    | 否（默认） | 是        |
| 典型用途      | 变量声明  | 精确类型获取   |

示例：

```cpp
int x = 0;
int& r = x;

auto a = r;            // int
decltype(r) b = x;     // int&
```

---

### 四、特殊规则与陷阱

#### 1️⃣ 花括号初始化

```cpp
auto x = {1, 2, 3};    // std::initializer_list<int>
```

而：

```cpp
auto x{1};             // int（C++17 起）
```

> 多元素 `{}` 直接推导为 `initializer_list`。

---

#### 2️⃣ 函数与数组退化

```cpp
int arr[10];
auto x = arr;          // int*
auto& y = arr;         // int (&)[10]
```

```cpp
void foo();
auto f = foo;          // void (*)()
```

---

### 五、`auto` 在 STL 与现代 C++ 中的角色

* 避免冗长模板类型
* 提升泛型代码可读性
* 与范围 `for`、迭代器、Lambda 强绑定
* 减少类型不一致导致的隐式转换风险

```cpp
for (auto it = v.begin(); it != v.end(); ++it) {}
for (auto& e : v) {}
```

---

### 六、编译器视角（简化流程）

1. 解析初始化表达式 AST
2. 套用模板推导规则
3. 生成确定类型
4. 替换 `auto`，参与后续语义与代码生成

---

### 七、工程建议

* 默认使用 `auto` 表达“类型由初始化决定”
* 需要引用或 `const` 时显式写 `auto& / const auto&`
* 接口边界、头文件慎用 `auto`，避免语义模糊

---

一句话总结：
**`auto` 的底层并非魔法，而是模板参数推导规则在变量声明上的一次复用。**

## **`std::move` 的底层机制**

---

### 一、本质结论

`std::move` **不做任何移动操作**，也**不搬数据**。
其唯一作用是：**在编译期将表达式强制转换为右值引用类型**，从而触发移动语义。

一句话：
**`std::move` = 右值类型转换工具。**

---

### 二、标准定义（核心实现）

标准库中的本质实现可等价表示为：

```cpp
template<class T>
constexpr std::remove_reference_t<T>&& move(T&& t) noexcept {
    return static_cast<std::remove_reference_t<T>&&>(t);
}
```

关键点拆解：

* `T&&`：万能引用，接受左值 / 右值
* `remove_reference_t<T>`：去掉引用，避免 `T& &&`
* `static_cast<...&&>`：强制转为右值引用
* `noexcept`：保证容器优先选择移动而非拷贝

---

### 三、编译器视角发生了什么

```cpp
std::string s = "abc";
std::string t = std::move(s);
```

编译期过程：

1. `s` 是左值
2. `std::move(s)` → `static_cast<std::string&&>(s)`
3. 表达式“看起来像右值”
4. 构造 `t` 时，**匹配到移动构造函数**

```cpp
string(string&& other);
```

---

### 四、为何必须显式调用 `std::move`

原因：
**具名对象永远是左值**，即使其类型是 `T&&`。

```cpp
void f(std::string&& s) {
    auto a = s;            // 拷贝
    auto b = std::move(s); // 移动
}
```

`s` 有名字 → 左值 → 不会自动触发移动。

---

### 五、与拷贝 / 移动的关系

| 操作          | 是否移动资源   |
|-------------|----------|
| 拷贝构造        | 否        |
| 移动构造        | 是        |
| `std::move` | 否（只转换类型） |

> **真正的移动发生在构造函数 / 赋值运算符内部。**

---

### 六、`std::move` 的误区

#### 1️⃣ 调用后对象并未销毁

```cpp
std::string s = "abc";
auto t = std::move(s);
```

`s` 仍然存在，仅处于“被移动后但有效”的状态。

---

#### 2️⃣ 滥用 `std::move`

```cpp
const std::string s = "abc";
auto t = std::move(s);   // 拷贝，不是移动
```

原因：

* `const T&&` 不能绑定到 `T&&` 移动构造
* 退化为拷贝构造

---

### 七、与 `std::forward` 的对比

| 工具                | 用途            |
|-------------------|---------------|
| `std::move`       | **无条件** 转为右值  |
| `std::forward<T>` | **条件性** 保留值类别 |

```cpp
template<typename T>
void f(T&& x) {
    g(std::forward<T>(x));   // 完美转发
}
```

---

### 八、工程实践要点

* 表示“资源不再使用”时才调用 `std::move`
* 移动构造 / 赋值应保证对象仍可析构
* 容器类型的移动构造建议 `noexcept`
* 返回局部变量无需 `std::move`（NRVO）

---

一句话总结：
**`std::move` 只是一次右值引用的显式标注，真正的“移动”由类型的移动构造 / 移动赋值完成。**

## **ROS 中的时间同步机制（工程视角）**

---

### 一、时间体系划分

ROS 中存在三类时间源：

* **Wall Time**：系统真实时间
* **ROS Time**：`/clock` 话题驱动的逻辑时间
* **Sim Time**：仿真时间（Gazebo / Bag）

> 所有时间同步问题，本质都是**时间源一致性问题**。

---

### 二、节点内部时间获取

* `ros::Time::now()`（ROS1）
* `rclcpp::Clock().now()`（ROS2）

关键点：

* 开启 `use_sim_time` 后，时间完全依赖 `/clock`
* `/clock` 未发布前，时间停滞

---

### 三、消息级时间同步（核心）

#### 1️⃣ 时间戳来源

* **传感器硬件时间**（理想）
* **驱动打时间戳**
* **接收时打时间戳（最差）**

优先级：
**硬件时间 > 驱动层 > ROS 回调**

---

#### 2️⃣ `message_filters` 同步机制

**ExactTime（严格同步）**

* 时间戳完全一致才触发回调
* 适合同一硬件或同一触发源

**ApproximateTime（近似同步）**

* 允许时间窗口误差
* 工程中最常用

核心参数：

* queue size
* slop（允许时间偏差）

---

### 四、典型同步模式

#### ① 多传感器融合（激光 + 相机 + IMU）

* 所有消息使用统一时间基准
* IMU 频率最高，作为主时钟参考
* 其余传感器向 IMU 时间对齐

---

#### ② 双机 / 多处理器系统

* 系统时间通过 **NTP / PTP** 对齐
* ROS 层只负责逻辑同步
* 禁止混用未对齐系统时间

---

#### ③ 嵌入式 + ROS 主机

* MCU 时间 → 主机时间映射
* 上行数据附带 MCU tick
* ROS 侧做时间重建与漂移补偿

---

### 五、常见问题与对策

| 现象                  | 根因           | 对策             |
|---------------------|--------------|----------------|
| 回调不触发               | ExactTime 严格 | 改用 Approximate |
| 数据延迟大               | 队列过深         | 减小 queue       |
| 时间跳变                | /clock 不稳定   | 固定时间源          |
| TF 报错 extrapolation | 未来 / 过去时间    | 对齐时间戳          |

---

### 六、TF 与时间的关系

* TF 查找严格依赖时间
* 传感器时间 ≠ TF 时间会直接失败
* 发布 TF 必须使用同一时间基准

经验法则：

> **先统一时间，再谈坐标。**

---

### 七、工程实践建议

* 硬件支持时间戳优先使用
* 不同设备先做系统时间同步
* ROS 中避免“回调打时间戳”
* 融合算法显式检查时间差
* 记录原始时间与 ROS 时间

---

### 八、调试手段

* `rostopic echo header.stamp`
* `rosbag info` 查看时间分布
* 打印 Δt 而非绝对时间
* 可视化时间轴对齐情况

---

一句话总结：
**ROS 时间同步的核心不是 API，而是时间源统一、时间戳可信，以及同步策略与工程现实的匹配。**

## **ROS 中的“时间”是什么**

---

### 一、本质定义

ROS 中的时间并不等同于操作系统时间。
其本质是：**由 ROS 抽象出的统一时间轴，用于标记消息、驱动同步与推理顺序。**

> ROS 关心的不是“现在几点”，而是“这条数据发生在什么时候”。

---

### 二、三种时间概念

#### 1️⃣ Wall Time（系统时间）

* 来源：操作系统时钟
* 特点：单调递增，真实世界时间
* 用途：日志、性能统计、现实运行

---

#### 2️⃣ ROS Time（逻辑时间）

* ROS 提供的统一时间接口
* 默认等同于 Wall Time
* 可被 `/clock` 覆盖

获取方式：

* ROS1：`ros::Time::now()`
* ROS2：`rclcpp::Clock(RCL_ROS_TIME).now()`

---

#### 3️⃣ Sim Time（仿真时间）

* 由 `/clock` 话题发布
* 可暂停、回放、加速、倒退
* 广泛用于仿真与 rosbag

> 开启 `use_sim_time` 后，ROS Time 完全依赖 `/clock`。

---

### 三、为什么 ROS 要“造时间”

解决三个核心问题：

* **多节点一致性**
  不同节点对“同时”的理解必须一致
* **可回放性**
  同一份数据多次运行结果一致
* **多传感器对齐**
  数据顺序由时间而非到达顺序决定

---

### 四、消息中的时间

ROS 消息通常包含：

```text
std_msgs/Header
 ├─ stamp   ← 关键
 └─ frame_id
```

`stamp` 表示：

* 数据**实际发生的时间**
* 而非被接收、被处理的时间

这是 TF、SLAM、融合算法的时间基石。

---

### 五、时间在系统中的作用链

```text
时间戳
  ↓
消息同步
  ↓
TF 查询
  ↓
状态估计 / 融合
  ↓
控制决策
```

时间一旦混乱，后续模块将整体失效。

---

### 六、常见误解

* ❌ 时间只是用来打印日志
* ❌ ROS 时间一定等于系统时间
* ❌ 用回调时间戳就足够

正确理解：

> **时间是 ROS 中隐性的全局协议。**

---

### 七、工程经验

* 优先使用硬件时间戳
* 所有节点使用同一时间源
* TF、传感器、融合算法时间一致
* 不混用 Wall Time 与 Sim Time
* 显式感知时间跳变与暂停

---

一句话总结：
**ROS 中的时间是一条可被控制、可被回放、必须统一的逻辑时间轴，是整个系统正确运行的前提。**

## **ROS 是什么**

---

### 一、本质定义

ROS（Robot Operating System）并不是操作系统。
其本质是：**面向机器人系统的分布式软件中间件与工程框架**。

> 提供通信机制、时间体系、工具链与工程范式，而非调度 CPU 或管理内存。

---

### 二、核心解决的问题

机器人软件的共性难题：

* 多进程 / 多节点协同
* 传感器与执行器解耦
* 数据流与控制流组织
* 时间、坐标、同步一致性
* 快速集成与复用

ROS 对这些问题给出统一答案。

---

### 三、ROS 的核心组成

#### 1️⃣ 通信机制

* **Topic**：发布 / 订阅（数据流）
* **Service**：请求 / 响应（同步调用）
* **Action**：可取消、带反馈的长任务

实现目标：
**模块间低耦合通信。**

---

#### 2️⃣ 节点（Node）

* 独立进程或组件
* 功能单一、职责明确
* 可分布在不同设备

---

#### 3️⃣ 消息（Message）

* 严格定义的数据结构
* 支撑跨语言通信
* 以时间戳为核心

---

#### 4️⃣ 时间与坐标

* 统一时间源（ROS Time）
* TF / TF2 坐标变换树
* 支撑感知、定位、控制

---

#### 5️⃣ 工具链

* 构建系统（catkin / colcon）
* 调试工具（rosbag、rviz、rqt）
* 参数服务器 / 参数系统

---

### 四、ROS 的工程角色

在机器人系统中的位置：

```text
应用算法
────────────
ROS 通信 / 时间 / TF
────────────
驱动 / 硬件接口
────────────
操作系统（Linux / RTOS）
```

ROS 位于**算法与硬件之间**。

---

### 五、ROS 适合做什么

* 机器人系统集成
* 多传感器融合
* SLAM / 感知 / 规划
* 仿真与现实无缝切换
* 快速原型与教学

---

### 六、ROS 不适合做什么

* 硬实时电机控制
* 超低延迟闭环（µs 级）
* 强安全认证系统
* 单片机裸机控制

---

### 七、ROS1 与 ROS2 的差异定位

* ROS1：研究与原型友好
* ROS2：工业化、实时性、多机支持

---

### 八、常见误解

* ❌ ROS = 操作系统
* ❌ ROS = 某个算法
* ❌ 装了 ROS 就能自动跑机器人

---

一句话总结：
**ROS 是一套为机器人系统提供“通信、时间、坐标与工程规范”的软件基础设施，而不是操作系统本身。**

## **ROS 中的 Topic、Service、Action**

---

### 一、整体视角

三者是 ROS 的三种通信范式，分别对应三类问题：

| 机制      | 解决的问题  |
|---------|--------|
| Topic   | 持续数据流  |
| Service | 一次性请求  |
| Action  | 可控的长任务 |

---

### 二、Topic（发布 / 订阅）

**定位**：异步、持续的数据通道

**特征**

* 一对多 / 多对多
* 无返回值、无状态
* 数据以时间戳为核心
* 适合高频传感器与状态发布

**典型场景**

* 激光雷达、相机、IMU
* 里程计、状态估计
* 控制指令流

**工程理解**

> Topic 描述“世界在发生什么”。

---

### 三、Service（请求 / 响应）

**定位**：同步调用的函数式接口

**特征**

* 一请求一响应
* 调用方阻塞等待结果
* 强因果关系
* 不适合高频

**典型场景**

* 参数设置
* 模式切换
* 状态查询

**工程理解**

> Service 描述“问一次，答一次”。

---

### 四、Action（目标 / 反馈 / 结果）

**定位**：可取消、可反馈的长时任务

**内部机制**

* 基于 Topic 封装
* 包含：Goal / Feedback / Result
* 支持 Cancel

**特征**

* 非阻塞
* 有进度反馈
* 可中途终止

**典型场景**

* 导航到目标点
* 机械臂抓取
* 路径跟踪

**工程理解**

> Action 描述“做一件事，并随时汇报进展”。

---

### 五、三者对比总结

| 维度    | Topic | Service | Action |
|-------|-------|---------|--------|
| 通信模式  | 异步流式  | 同步请求    | 异步任务   |
| 是否阻塞  | 否     | 是       | 否      |
| 是否有反馈 | 否     | 否       | 是      |
| 是否可取消 | 否     | 否       | 是      |
| 使用频率  | 高频    | 低频      | 中频     |
| 时间跨度  | 瞬时    | 瞬时      | 长时间    |

---

### 六、设计选型经验

* **数据持续变化** → Topic
* **一次性操作** → Service
* **耗时且需监控** → Action

判断准则：

> 是否需要“过程”和“取消能力”。

---

### 七、常见误用

* 用 Service 传高频数据
* 用 Topic 做必须应答的控制
* 用 Topic 代替 Action 的任务状态

---

一句话总结：
**Topic 表达状态流，Service 表达请求，Action 表达任务过程，三者共同构成 ROS 的通信语义基础。**

## **左值、右值与万能引用（C++）**

---

### 一、左值与右值的本质

C++ 中的值类别，描述的不是“能否放在等号左边”，而是**表达式与对象生命周期、身份的关系**。

#### 左值（lvalue）

**特征**

* 有稳定身份
* 可被多次引用
* 有明确存储位置

**典型例子**

```cpp
int x = 10;   // x 是左值
*x           // 左值
```

直观理解：

> **能被“指认”的对象。**

---

#### 右值（rvalue）

**特征**

* 临时对象
* 无稳定身份
* 生命周期通常很短

**典型例子**

```cpp
10
x + 1
std::string("abc")
```

直观理解：

> **即将被销毁的临时结果。**

---

### 二、更细的值类别（现代 C++）

```text
         expression
        /           \
     glvalue        rvalue
     /    \           |
 lvalue   xvalue    prvalue
```

工程中重点关注：

* **lvalue**：有名字、有身份
* **xvalue**：即将被移动的对象
* **prvalue**：纯临时值

`std::move(x)` 的结果是 **xvalue**。

---

### 三、引用类型对值类别的绑定规则

| 引用类型       | 可绑定对象   |
|------------|---------|
| `T&`       | 仅左值     |
| `const T&` | 左值 / 右值 |
| `T&&`      | 仅右值     |

---

### 四、什么是“万能引用”（Universal Reference）

**定义条件（缺一不可）**

1. 形如 `T&&`
2. `T` 通过模板参数推导得到

```cpp
template<typename T>
void f(T&& x);   // 万能引用
```

> 只有在模板推导场景下，`T&&` 才是万能引用。

---

### 五、万能引用的推导规则（引用折叠）

```text
T&  &  → T&
T&  && → T&
T&& &  → T&
T&& && → T&&
```

推导结果：

```cpp
int a = 0;

f(a);        // T = int&  → x 类型 int&
f(10);       // T = int   → x 类型 int&&
```

结论：

* 左值传入 → 左值引用
* 右值传入 → 右值引用

---

### 六、万能引用的真正用途

**完美转发（Perfect Forwarding）**

```cpp
template<typename T>
void wrapper(T&& x) {
    g(std::forward<T>(x));
}
```

* 保留原始值类别
* 不强制移动、不强制拷贝

---

### 七、常见误区

#### ❌ 所有 `T&&` 都是万能引用

只有模板推导 + `T&&` 才成立。

```cpp
void f(int&& x);     // 右值引用，不是万能引用
```

---

#### ❌ `std::move` 等于移动

`std::move` 只是类型转换，是否移动取决于构造 / 赋值函数。

---

### 八、工程记忆法

* **左值**：有名字、可复用
* **右值**：临时的、可被“榨干”
* **万能引用**：既接左值，也接右值
* **`std::forward`**：还原其本来面目

---

一句话总结：
**左值描述对象身份，右值描述对象生命周期，万能引用是为“不丢失值类别”而生的模板工具。**

## **机器人控制中的周期控制模型**

在机器人或电机控制系统中，
通常不会用命令式的串口调用来做控制，
而是采用周期控制模型。

上层或中间层会维护一块共享的控制状态和指令区，
控制线程按固定周期读反馈、写目标，
通信和驱动层负责保证数据在每个周期被刷新。

这种方式的优势是低延迟、低抖动和可预测性，
更适合实时控制系统。

# 机器人中间层 C++ / ROS 面试「标准答案速查表」

> **定位说明**：
> 本速查表面向 **机器人 / ROS / 中间层 C++ 工程师** 岗位，
> 不要求电机硬件实操，但强调 **系统观、实时性意识、现代 C++ 机制理解**。

---

## 一、ROS 基础与系统观（高频）

### 1. ROS 是什么？

**标准回答：**

> ROS 是一个用于机器人系统的软件框架，提供了通信机制、时间系统、工具链和生态，
> 用于解耦感知、规划、控制等模块，本质上是一个**分布式机器人中间件**，而不是操作系统。

**关键词：** 中间件、分布式、模块解耦

---

### 2. ROS 中的 Topic / Service / Action

| 机制      | 特点            | 使用场景      |
|---------|---------------|-----------|
| Topic   | 异步、发布订阅       | 传感器数据、状态流 |
| Service | 同步、请求-响应      | 配置、一次性查询  |
| Action  | 异步 + 反馈 + 可取消 | 导航、机械臂运动  |

**一句话总结：**

> Topic 传流，Service 查结果，Action 管长任务。

---

### 3. ROS 中的“时间”是什么？

**标准回答：**

> ROS 中的时间是一个**可抽象、可替换的时间源**，
> 支持真实时间、仿真时间和逻辑时间，用于保证多节点时间一致性。

**延伸点：**

* `ROS time` ≠ `system time`
* 支持 `/use_sim_time`

---

### 4. ROS 中的时间同步机制（工程视角）

**标准回答：**

> ROS 的时间同步本质是**基于时间戳的软件同步**，
> 通过统一时间源和时间戳对齐，实现多传感器数据的时序一致。

**补充：**

* message_filters
* 硬件同步 vs 软件同步

---

## 二、实时性与中间层设计（核心）

### 5. 什么是实时系统？

**标准回答：**

> 实时系统强调的是**确定性**，而不是极致速度。
> 软实时允许偶尔超时，硬实时不允许。

**关键一句：**

> 控制系统更怕抖动，而不是慢。

---

### 6. 为什么机器人控制不用普通串口调用？

**标准回答：**

> 串口调用是命令式、非周期的，延迟和抖动不可控。
> 机器人控制通常采用**周期控制模型**，
> 通过固定周期读写共享状态，保证确定性。

---

### 7. 共享内存 vs 消息队列

| 对比项 | 共享内存    | 消息队列  |
|-----|---------|-------|
| 拷贝  | 少 / 零拷贝 | 多次拷贝  |
| 延迟  | 低       | 较高    |
| 适用  | 控制、实时   | 业务、解耦 |

---

## 三、现代 C++（必考机制）

### 8. auto 的底层机制

**标准回答：**

> auto 基于模板类型推导规则，
> 会丢失顶层 const，但保留底层 const，
> 是否保留引用取决于是否写 `auto&` / `auto&&`。

---

### 9. std::move 的底层机制

**标准回答：**

> std::move 本质是一次 `static_cast<T&&>`，
> 它并不移动对象，只是把对象标记为“可被移动”。

**补充：**

> 是否真的发生移动，取决于类型是否实现了移动构造/赋值。

---

### 10. 拷贝构造 vs 移动构造

| 项目 | 拷贝 | 移动 |
|----|----|----|
| 资源 | 复制 | 窃取 |
| 成本 | 高  | 低  |
| 触发 | 左值 | 右值 |

**关键点：**

* move 后对象仍需保持可析构状态
* 返回值优化（RVO / NRVO）

---

### 11. RAII 是什么？

**标准回答：**

> RAII 是一种资源管理范式，
> 将资源的生命周期绑定到对象的构造和析构，
> 保证异常安全和资源正确释放。

---

### 12. 智能指针使用场景

| 指针         | 场景     |
|------------|--------|
| unique_ptr | 独占资源   |
| shared_ptr | 多方共享   |
| weak_ptr   | 打破循环引用 |

---

## 四、并发与性能（中间层必问）

### 13. 为什么实时线程要避免 new/delete？

**标准回答：**

> 动态内存分配会引入不可预测延迟和碎片，
> 在实时系统中会破坏确定性。

---

### 14. mutex vs spinlock

|    | mutex | spinlock |
|----|-------|----------|
| 阻塞 | 会     | 不会       |
| 适合 | 长临界区  | 短临界区     |

---

### 15. 哪些操作不能放在控制线程？

* IO（磁盘 / 网络）
* 动态内存分配
* 日志打印
* 复杂锁竞争

---

* **ROS 是中间件，不是库**
* **控制系统追求确定性，而不是吞吐**
* **std::move 只是类型转换**
* **auto ≈ 模板推导规则**
* **中间层关注数据流和时序，不碰硬件细节**
